# Minecraft 26.3 SDL3 / Xbox UWP path

Minecraft 26.3 no longer uses LWJGL GLFW for its window/input backend. This project therefore keeps the existing `glfw.dll` UWP shim only for Minecraft 26.2 and older. Minecraft 26.3+ loads `org.lwjgl.sdl` directly and is forced to the packaged UWP `SDL3.dll` with `org.lwjgl.sdl.libname`.


### V13: external-host input bridge

V13 intentionally leaves the V12 Mesa/WGL sequence unchanged. It hardens only the WinRT input layer used after SDL attaches to Bandit's externally-owned `CoreWindow`.

SDL's WinRT cursor fallback used `CoreWindow.PointerCursor = nullptr` when its optional transparent cursor resource was unavailable. SDL's own source warns that this suppresses CoreWindow pointer-motion events. The Bandit host does not rely on that resource, so V13 keeps a stock cursor as the safe fallback instead of sacrificing mouse motion.

For first-person input, SDL still consumes raw relative deltas from `Windows.Devices.Input.MouseDevice::MouseMoved`; menu input continues through CoreWindow pointer events. The subscription is null-safe when no physical mouse is connected. One-time log markers prove the absolute and relative halves of the input bridge independently:

- `Bandit SDL V13: first absolute CoreWindow mouse motion delivered`
- `Bandit SDL V13: first raw MouseDevice relative delta delivered`
- `Bandit SDL V13: relative mouse mode=1`
- `Bandit SDL V13: relative mouse mode=0`

The launcher separately verifies the version-specific Bandit controller jar when controller support is enabled, so controller-as-cursor support cannot silently disappear from a package.

## Runtime used by the build

`build.ps1` runs `scripts/prepare-sdl3-uwp.ps1`. By default that script:

1. fetches the pinned XboxEmulationHub SDL3-UWP source commit;
2. patches its WinRT backend for Bandit's externally-owned `IFrameworkView` / `CoreWindow` **and** enables SDL's WinRT-safe Windows shared-object loader for WindowsStore builds;
3. builds an x64 WindowsStore/UWP `SDL3.dll` with Visual Studio/CMake;
4. validates the resulting PE architecture, Bandit V7 lifecycle and V8 provider-parity markers, and the SDL exports used by the 26.3 launch/controller path;
5. stages the runtime as `natives/SDL3.dll`.

The proven V6 base patch is recorded in `patches/sdl3-uwp-external-host.patch`; V7 applies the deterministic, anchor-checked `scripts/apply-sdl3-v7-wgl.ps1` lifecycle transform, V8 applies `scripts/apply-sdl3-v8-provider-parity.ps1`, V9 applies `scripts/apply-sdl3-v9-stability.ps1`, V12 applies `scripts/apply-sdl3-v12-renderpearl-contract.ps1`, V13 applies `scripts/apply-sdl3-v13-input.ps1`, and V14 applies `scripts/apply-sdl3-v14-input.ps1` to force the UWP WGI controller backend and add a relative-mouse fallback. V10 is deliberately not applied: source-level verification of Minecraft 26.3 showed that RenderPearl creates one OpenGL context and later rebinds it to the final game window, so the V10 multi-context premise was incorrect. All active patch inputs are included in the content-addressed cache identity. Editing the patch or build configuration therefore cannot silently reuse an older DLL.

A developer may set `SDL3_UWP_DLL` to bypass the source build. The override is still validated and must be x64, export `BanditSDL_ExternalHostPatchVersion`, `BanditSDL_WinRTIntegrationPatchV7`, `BanditSDL_WinRTProviderParityV2`, `BanditSDL_WinRTStabilityV9`, `BanditSDL_WinRTRenderPearlV12`, `BanditSDL_WinRTInputBridgeV13`, `BanditSDL_WinRTInputBridgeV14`, the WGL-only `BanditSDL_WinRTWGLBackendV1`, `BanditSDL_WinRTSafeWGLInitV1`, `BanditSDL_WinRTMultiWindowV1`, and `BanditSDL_WinRTAbsoluteLoadFixV1` markers, and export the SDL entry points required by this project. A stock desktop SDL3 DLL and an unpatched SDL3-UWP binary are rejected.

## Why the SDL fork needs a patch

The SDL WinRT backend normally owns the application's `IFrameworkView`. Bandit already owns that UWP view before Java starts. Without adaptation, SDL can discover the current `CoreWindow` and create its SDL window, but `SDL_WinRTGlobalApp` is never created. That leaves `SDL_PollEvent()` without the WinRT event pump and leaves SDL's keyboard, mouse, text, visibility, and activation handlers unattached.

The patch creates SDL's normal `SDL_WinRTApp` event sink after `WINRT_GlobalSDLWindow` is assigned and attaches it to the existing `CoreWindow`. It also fixes the fork's CMake WindowsStore path to compile `src/loadso/windows/SDL_sysloadso.c` instead of falling back to SDL's dummy loader. That Windows loader is explicitly WinRT-aware and uses `LoadPackagedLibrary`. V7 has distinct exported markers so an older CoreWindow/loadso/SDL-main-only Bandit SDL binary cannot be substituted accidentally. V7 also handles SDL's `SDL_main` readiness gate: Bandit launches Java from an already-running UWP `IFrameworkView`, so SDL's normal WinRT bootstrap never calls `SDL_SetMainReady()`. The patched runtime marks SDL main-ready lazily on the first `SDL_InitSubSystem` call before Mojang's renderer initializes SDL. Minecraft continues to call ordinary SDL/LWJGL APIs; there is no GLFW-to-SDL compatibility layer in the 26.3 path.

Minecraft is launched synchronously from the launcher's UWP `IFrameworkView::Run()` call chain. SDL window creation and event pumping therefore begin on the same CoreWindow-owning thread. The launcher logs that thread ID for the first 26.3 launch so a future threading refactor is visible in diagnostics.

## OpenGL

For 26.3 the launcher sets:

- `org.lwjgl.sdl.libname` to the target-native UWP `SDL3.dll`;
- `SDL_VIDEO_DRIVER=winrt` (and the legacy `SDL_VIDEODRIVER` alias);
- `SDL_OPENGL_LIBRARY=graphics\mesa\opengl32.dll`, a package-relative path to the Mesa copy staged inside the APPX;
- `org.lwjgl.opengl.libname` to that Mesa runtime;
- `SDL_LOGGING=video=debug,input=info,error=debug` for useful first-run diagnostics.

The SDL3-UWP WinRT backend is built with desktop OpenGL/WGL enabled and OpenGL ES/EGL disabled. The external-host patch also prefers WGL if both backends are ever enabled accidentally. This is why Mesa's WGL exports remain part of the graphics runtime. Mojang's 26.3 `GlBackend.loadLibrary()` explicitly passes `((SharedLibrary) GL.getFunctionProvider()).getPath()` to `SDL_GL_LoadLibrary()`, so the game's absolute LWJGL provider path overrides the `SDL_OPENGL_LIBRARY` hint. On Xbox that becomes an absolute `S:\Program Files\WindowsApps\...\graphics\mesa\opengl32.dll` path. `LoadPackagedLibrary` rejects absolute paths, so the SDL loader detects Bandit's packaged Mesa suffix and normalizes it back to `graphics\mesa\opengl32.dll` before loading. LWJGL continues using its absolute Mesa path. `build.ps1` also stages Mesa dependencies at the APPX root so dependency lookup remains inside the package graph.


### V7 WGL lifecycle corrections

The first successful V6 hardware run reached Mesa and then crashed with a native `EXCEPTION_ACCESS_VIOLATION`. A full 26.3 startup audit found three structural problems in the fork's WinRT/WGL path, all fixed together in V7:

1. `WIN_GL_LoadLibrary()` created a temporary WGL probe context before Minecraft had created any SDL window. On WinRT/Mesa-UWP that meant probing a CoreWindow token before SDL had established its real window/pixel-format lifecycle. V7 defers WGL extension probing until the first real OpenGL context is current.
2. The WinRT window path never called `WIN_GL_SetupWindow()`, unlike SDL's desktop Windows backend. V7 sets the Mesa pixel format/framebuffer on the real CoreWindow before `wglCreateContext`; later logical SDL windows reuse that one physical pixel format because WGL permits `SetPixelFormat` only once.
3. Upstream WinRT rejects a second SDL window, but Minecraft 26.3's RenderPearl startup deliberately creates an OpenGL utility window, a second hidden test window, and later the real game window. V7 virtualizes those logical `SDL_Window` objects over the single Xbox `CoreWindow` and routes WinRT events to the newest live logical window.

V7's first provider-parity attempt preferred the Mesa DLL export before `wglGetProcAddress`. Hardware testing reached Minecraft's backend check but failed with `glGetError mismatch`. LWJGL's Windows OpenGL provider actually resolves functions through `wglGetProcAddress` first and only falls back to the loaded DLL export. V8 mirrors that exact order in SDL and emits a targeted `Bandit SDL V8: glGetError LWJGL-order pointer=...` diagnostic. Risky WGL context/make-current/swap calls remain guarded on MSVC/WinRT so a driver structured exception becomes a useful SDL error instead of an opaque JVM `EXCEPTION_ACCESS_VIOLATION`. The fork's stale WinRT declaration of `WIN_SetError` is corrected from `int` to `bool`; otherwise a `-1` failure could be interpreted as `true` by WGL functions.

### V8 OpenGL provider parity

V8 is intentionally a small transform layered after V7. It does not undo the proven CoreWindow, multiwindow, pixel-format or WGL-lifecycle work. It only changes `WIN_GL_GetProcAddress` back to LWJGL-compatible Windows semantics: call Mesa's `wglGetProcAddress` first, then use `GetProcAddress` on the already-loaded `opengl32.dll` only when WGL returns null. The V8 script validates that ordering before it writes the patched source, the SDL build cache includes the V8 script hash, and packaged/override runtimes must export `BanditSDL_WinRTProviderParityV2`.


### V12: RenderPearl and Mesa framebuffer contract

Hardware testing of V9, V10 and V11 converged on the same stable black screen. The actual Minecraft 26.3 OpenGL source changes the diagnosis: RenderPearl creates one GL context on a hidden utility window, creates and destroys a second test window without a second context, then rebinds the original context to the final game window. V10's single-physical-context wrapper is therefore removed from the active build.

V12 instead corrects the Mesa drawable/pixel-format lifecycle. Disassembly of the bundled Mesa WGL DLLs shows that `wglGetPixelFormat` enters Mesa's `stw_pixelformat_get` path and may create framebuffer state. V7 called it before installing the requested pixel format, so the CoreWindow default framebuffer could be instantiated under an implicit/default contract. The Series-S-proven `glfw_shim/wgl_backend.h` path never performs that query: it chooses the format through `opengl32!wglChoosePixelFormat` and installs the chosen index through the lightweight `libgallium_wgl!SetPixelFormat` export. V12 mirrors that sequence exactly and performs it once for the physical CoreWindow.

The attributed-context path is also strict in V12. Minecraft requests OpenGL 3.3 core; SDL is no longer allowed to keep a temporary legacy context if `wglCreateContextAttribsARB` is unavailable. After binding the final context, SDL queries `GL_VERSION`, `GL_MAJOR_VERSION`, `GL_MINOR_VERSION`, profile mask, flags, vendor, renderer and GLSL version from the actual driver and rejects a context below the requested version/profile. The temporary base context is unbound with `wglMakeCurrent(NULL, NULL)` before deletion, matching the project's known-good Xbox Mesa sequence.

Finally, the WinRT window backend preserves RenderPearl's logical hidden/utility/high-DPI flags and acknowledges Xbox-inapplicable position/size/sync operations synchronously. The launcher preloads the Mesa support stack (`dxil.dll`, zlib, SPIR-V/DXIL translator, optional DZN, Gallium, then the exact `graphics\mesa\opengl32.dll` provider) before the JVM so SDL and LWJGL share one initialized provider stack.


## Controller support

Fabric 26.3 has a dedicated controller variant. It no longer imports or calls GLFW:

- SDL3/LWJGL handles gamepad discovery, connection state, axes, buttons, and mouse state;
- vanilla `InputConstants` supplies 26.3 scancodes and mouse-button IDs;
- Minecraft's 26.3 text-input focus API is used for chat, signs, edit boxes, and multiline edit boxes;
- the old GLFW native keyboard bridge is a no-op on 26.3;
- the old `GameRenderer.render(DeltaTracker, boolean)` injection was moved to the 26.3 `GameRenderer.extract(DeltaTracker, boolean)` phase;
- recipe-book and inventory accessors are maintained in a dedicated 26.3 overlay.

Forge and NeoForge 26.3 controller mappings have **not** been validated yet. Their catalog entries intentionally use controller provider `none`, and the launcher shows Bandit Controller as unavailable for those targets rather than advertising unsupported input.

## Compatibility mod

26.3 has its own compatibility overlay instead of silently reusing the 26.2 folder. The vanilla injection targets used by the overlay have been checked against 26.3 (`Minecraft.run`, `FileUtil.createDirectoriesSafe`, `FileSystemUtil.safeGetPath`, and `SystemReport.putHardware`). Optional third-party mixins remain optional and still require runtime testing with the actual mod version.

## Target-specific natives and manifests

A 26.3 target must prepare its own Mojang/Fabric launch metadata and target-specific LWJGL 3.4.3 native set. The launcher does not fall back to the package's older default LWJGL DLL for 26.3. Package validation checks that each 26.3 manifest includes the expected LWJGL core, OpenGL, SDL, and jemalloc native artifacts and that `natives/SDL3.dll` is present.

Fabric, Forge, and NeoForge are separate launch targets. A catalog row is not proof that all three work: each loader still needs its own build/package/runtime verification.

## Build and package acceptance test

On Windows with Visual Studio C++/UWP tools, Windows SDK, Java 25, CMake, Mesa UWP, and the signing certificate configured, run:

```powershell
$env:MESA_UWP_DIR = "C:\path\to\mesa-uwp"
.\scripts\verify-26.3-build.ps1 -KeepStaging
```

The script checks source guardrails, builds and validates patched SDL3, prepares the real 26.3 Fabric cache, compares the patched UWP DLL against the matching LWJGL 3.4.3 desktop SDL runtime and requires every `SDL_*` export from that reference, compiles the dedicated 26.3 compatibility and Fabric controller mods, generates 26.3 manifests for the configured loaders, runs the full launcher build, signs the APPX, verifies the APPX signature, and validates its packaged version/native matrix. `-SkipPackage` can be used when only the SDL/mod/manifests build checks are wanted.

## Expected first-run log lines

A 26.3 launch should include lines similar to:

```text
LWJGL SDL3 library forced: ...\SDL3.dll
SDL3 WinRT/OpenGL environment: driver=winrt OpenGL=graphics\mesa\opengl32.dll (LWJGL=...\opengl32.dll)
SDL3 diagnostics enabled: video=debug,input=info,error=debug
SDL3 launch thread id=... (Minecraft main runs synchronously on the UWP IFrameworkView::Run thread)
```

SDL's own logging should also contain:


For a 26.3 run, the absence of new `glfw_uwp.log` activity is expected: the game no longer goes through the GLFW shim.

## Xbox runtime acceptance still required

A successful Windows compile/package is necessary but not sufficient. Before 26.3 is promoted beyond experimental, verify on Xbox Dev Mode:

- external CoreWindow attachment and event pumping;
- no duplicate launcher/SDL mouse or keyboard events;
- Mesa OpenGL context creation and requested GL attributes;
- frame presentation through title screen and in-world rendering;
- framebuffer dimensions, scaling, cursor alignment, and fullscreen behavior;
- relative mouse movement, capture/release, buttons, wheel, and sensitivity;
- keyboard movement, shortcuts, text entry, and Xbox on-screen keyboard behavior;
- Fabric controller discovery, movement, look, menu navigation, text entry, disconnect/reconnect, and focus changes;
- focus loss, suspend/resume, Minecraft exit, and relaunch without stale handlers or contexts;
- separate Fabric, Forge, and NeoForge launches;
- regression launches of 1.21.11 and 26.2 to confirm they still select the GLFW path.

The repository changes can establish the architecture, compile/package checks, and diagnostics, but the Xbox-only items above require a hardware run.
